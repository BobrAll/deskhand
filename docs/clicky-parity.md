# Smart Cursor × Clicky (heyclicky): разрыв и план сближения

Только анализ, код не меняем. Источники по Clicky: лендинг и чейнджлог
(heyclicky.com, v1.0.53–1.1.4, окт–ноя 2026).

---

## 1. Что на самом деле делает Clicky

Из лендинга и чейнджлога видно механику, а не маркетинг:

| Механика | Как это устроено |
|---|---|
| Вход | **Держишь хоткей и говоришь.** Отпустил — пошёл ответ «через пару секунд». Текст — вторичный путь. |
| Что видит | Видит **весь экран**, а не активное окно. «Если ты это видишь, Clicky это видит» — без плагинов и интеграций. |
| Что отдаёт | **Голос** (TTS, 130+ языков, 30 голосов) + **рисунок поверх экрана**: обводит, указывает, чертит 2D/3D прямо на твоём экране, рядом карточки с фото. |
| Где живёт | В **нокче**: пик, Home, чат, настройки — всё оттуда; карточки агентов «висят» на нокче. Не модальное окно, а постоянное присутствие. |
| Что делает руками | **Clicky drive**: с разрешения двигает мышь и печатает за тебя; Escape/движение мыши — вернуть контроль. Плюс агенты (задачи в фоне), Chrome-расширение, коннекторы, рутины. |
| Память | Помнит, что было на экране **раньше в этом разговоре** и разговоры по дням. |
| Позиционирование | «AI buddy», а не «AI tool»: характер, шутки, свой маскот, знаменитый онбординг. |
| Приватность как фича | Отдельная страница trust: «смотрим на экран только по хоткею, скриншоты не храним». |

Ключевое: у Clicky **нет** режимов «вставить / проанализировать». Есть «поговорить»,
«продиктовать», «сделать». Интерфейс — голос + вторая пара глаз поверх экрана.

## 2. Что сейчас у Smart Cursor (по коду)

- Вход: `Alt+Space` (`src/main/hotkey.ts`) → раскрывается карточка у курсора
  (`windows.ts:positionOverlay`) → **фокус забирается силой** (`win.focus()` +
  `app.focus({ steal: true })`).
- Контекст: front app через native helper → **выделение через синтетический ⌘C
  с подменой клипборда** (до 450 мс, `context/selection.ts`) → скриншот **только
  активного окна** (`screencapture -l windowId`), асинхронно после показа.
- Ввод: только `textarea`, Enter — отправить.
- Ответ: один поток текста в `.answer` (`overlay/App.tsx`), режимы `insert`
  (без markdown) и `analyze` (с markdown) в `prompt.ts`.
- Один выстрел: сессии живут от хоткея до закрытия, истории и памяти нет.
- Действия: copy / paste в исходное приложение (`paste/index.ts`), «короче/длиннее».
- Настройки: 4 секции (`settings/App.tsx`), онбординг = чек-лист разрешений
  + ключ API (`onboarding/App.tsx`).

Технически база приличная: native helper на ObjC свой, есть `front`, `cursor`,
`copy`, `paste`, `activate`, `permissions` — то есть половина нужных
macOS-примитивов уже написана.

## 3. Разрыв по осям

| Ось | Clicky | Smart Cursor | Разрыв |
|---|---|---|---|
| Способ ввода | голос (hold-to-talk) | клавиатура | **критичный** |
| Канал ответа | голос + рисунок на экране | текст в карточке | **критичный** |
| Что видит | весь экран | окно активного приложения | средний |
| Присутствие | постоянное (нокч), не крадёт фокус | модальная карточка, крадёт фокус | **критичный** |
| Действие | сам двигает мышь/печатает | только вставляет текст | большой (но поздний) |
| Память | диалог + история экрана | нет | средний |
| Модель ответа | «объясню/покажу/сделаю» | «перепиши текст» | **смысловой** |
| Характер | маскот, шутки, онбординг-история | нейтральный утилитарный UI | большой и дешёвый |
| Скорость | ответ через ~2 с после отпускания | хоткей → сбор (0.3–0.9 с) → поток | средний |

Главный вывод: разница не в фичах, а в **метафоре**. Smart Cursor — «умный буфер
обмена с промптом», Clicky — «собеседник, который смотрит на твой экран». Копировать
фичи по одной бессмысленно, надо сдвинуть метафору, а фичи уже прицепятся.

## 4. Четыре сигнатурные механики — как их повторить технически

### 4.1 Hold-to-talk — сделано

Уже в коде, вопрос закрыт:

- `smartcursor-helper voice <keyCode> <flags> swallow` держит `CGEventTap` на
  `kCGSessionEventTap` и печатает JSON-строки (`ready` / `press` / `release` /
  `cancel` / `reenabled`). Escape во время удержания — `cancel`; при
  `kCGEventTapDisabledByTimeout` tap включается обратно на месте. Комбинация
  проглатывается, поэтому не долетает до приложения под карточкой.
- Запись — в оверлей-рендерере (`getUserMedia` → `AudioContext`, 16 кГц моно
  16-бит WAV с обрезкой тишины по краям). Микрофон закрывается сразу после
  хода: незакрытый поток оставляет оранжевую точку в меню-баре.
- STT — локальный `whisper.cpp` (`resources/whisper-cli`, 3.8 МБ, universal,
  Metal внутри, `npm run build:whisper`). Модель качается из каталога
  `WHISPER_MODELS` в `userData/models`, уже лежащие `ggml-*.bin` подхватываются.
  Для RU по умолчанию `small-q5_1` — ~1.2 с на фразу на M2.
- Окно прогревается заранее (`overlayHost.prewarm()`), запись стартует по
  нажатию *до* сбора контекста: иначе терялся первый слог.
- Настройки: вкладка «Голос» — хоткей, модель со скачиванием, язык, действие
  (`command` / `dictate`), автоотправка.
- Ходы не пересекаются. Нажатие во время распознавания предыдущей фразы — это
  новая фраза, а не ошибка: прежний ход отменяется (`abort`), его результат
  отбрасывается по номеру хода, и карточка сразу показывает «слушаю» снова.
  Раньше такое нажатие молча игнорировалось, и анимация «не проигрывалась».
- Зависший ход закрывается сторожем: потерянный key-up обрывается по
  `voice.maxDurationMs`, не пришедшая от рендерера запись — через 5 с, зависший
  `whisper-cli` — через 30 с. Без этого карточка мигала «распознаю» вечно, а
  каждое следующее нажатие проглатывалось.

Осталось необязательное: стриминг промежуточного текста (сейчас текст
появляется только после распознавания целиком).

### 4.1.1 Индикатор «слушаю» — сделано (карточка, не капсула у курсора)

Индикатор ровно один и это **сама карточка**: на время хода поле ввода заменяется
пятью столбиками (`App.tsx`, ветка `if (listening)`), окно при этом теряет стекло,
рамку и тень (`setVoice(true)` → `applyWindowChrome`), а ширина сжимается до
`OVERLAY_VOICE_WIDTH = 80` pt — минимум, при котором macOS ещё не рисует
непрозрачный прямоугольник вместо прозрачного окна. Второго окна у курсора нет:
отдельная капсула (`src/main/hud.ts`, `src/renderer/hud/`) осталась в коде, но
её `update()` больше не вызывается — это легаси, а не действующий индикатор.

- «Слушаю» — столбики прыгают со сдвигом фазы; громкость открывает всю группу
  целиком через одну CSS-переменную с переходом 120 мс. Метр приходит 10 раз в
  секунду, и без перехода он читался бы как дрожь, а не как голос.
- «Распознаю…» — микрофон уже закрыт, поэтому прыгать нечему: столбики
  переходят в одну медленную волну слева направо и теряют акцент.
- Движение делает CSS на композиторе, `requestAnimationFrame` в рендерере нет
  вовсе: прозрачное окно, перерисовывающееся на 60 fps, — это перегрев ноутбука,
  который всплывает через пару дней.
- `prefers-reduced-motion` оставляет статичную карточку: состояние всё равно
  читается по появлению, по `aria-label` и по цвету столбиков.

Правило «ответ виден, работа агента — нет» держится на данных, а не на вёрстке:
строка ответа рисуется только при непустом `done.text` (`hasAnswer`), а
нарратив «нажимаю…» на голосовом ходу придерживается в main (`holdFirstRound`) и
не отдаётся вовсе, если план реально выполняется (`suppressed`). Проверки:
`.scratch/voice-fix-probe` (main: подавление, пустой ответ, look-then-action) и
`.scratch/voice-live` (настоящее окно + настоящий рендерер: ответ виден, у
действия строки ответа нет, второе нажатие снова анимируется).

### 4.2 Рисование поверх экрана

Самое ценное и самое «кликкиподобное». Схема:

1. Второе окно — прозрачный **full-screen overlay** на весь дисплей курсора:
   `frame:false, transparent:true, focusable:false`,
   `setIgnoreMouseEvents(true, { forward: true })`,
   `setAlwaysOnTop(true, 'screen-saver')`,
   `setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })`.
   Не показывается в Mission Control, не крадёт фокус, клики проходят насквозь.
2. Модель возвращает **нормализованные координаты** `0..1` относительно
   скриншота + подпись + тип (`circle` / `arrow` / `box` / `underline` / `card`),
   а не пиксели.
3. Маппинг в экранные точки:
   `screenX = win.bounds.x + nx * win.bounds.width` — **но** скриншот приходит в
   пикселях Retina (`bounds × devicePixelRatio`), поэтому `nx` считать от ширины
   *изображения*, а не окна, иначе всё уедет в 2 раза на Retina. Это главная
   ловушка; закрывается одной функцией `mapNormalizedToScreen()`.
4. Рендер: SVG-слой + анимация «маркер дорисовывается» (`stroke-dashoffset`) —
   это и есть узнаваемый почерк Clicky, и стоит он почти ничего.
5. Скриншот для этого нужен **дисплея, а не окна**: `screencapture -x` по дисплею
   курсора (или `-R` по bounds). Текущий `captureScreenshot` умеет только окно →
   добавить `CaptureTarget.mode: 'window' | 'display'`, при этом старый режим
   оставить для «перепиши текст в этом окне».
6. Модели плохо дают координаты. Лечится: строгая инструкция «координаты только
   внутри скриншота, центр объекта», валидация `0..1`, отбрасывание мусора,
   и **фолбэк**: если координат нет — карточка без рисунка, а не сломанная стрелка.
   Второй проход «где это на экране?» по уже полученному описанию — обычно точнее,
   чем один ответ с рисунком.

Цена: **3–4 дня** (окно + протокол + маппинг + анимация), но именно это даёт
«вау» на демо сильнее всего.

> **Реализовано.** Слой `src/main/pointer.ts` + `src/renderer/pointer/` (окно
> `pointer` — отдельный бандл), протокол `@point` в `src/main/annotations.ts`.
> Координаты нормализованы и считаются от прямоугольника *снимка*
> (`ScreenshotInfo.area`), а не от окна — поэтому Retina не требует деления на
> `scaleFactor` вовсе. Снимок берётся с дисплея (`CaptureTarget.fullDisplay`).
>
> **Рисование — инструмент, а не режим.** Тумблера «показать на экране» больше
> нет. Инструкция `DRAW_TOOL` (`src/main/prompt.ts`) добавляется к обычному
> запросу всякий раз, когда ассистент получает картинку, и уже сама говорит, когда
> рисовать (`где кнопка`, `куда нажать`), а когда нет (переписать, перевести,
> сократить). Решение — за моделью, пользователю переключать нечего: единственный
> переключатель — чип «Вижу экран», он же и включает/выключает инструмент, и без
> картинки инструмент не предлагается вовсе (координаты были бы выдуманы).
>
> Отличия от плана выше, принятые осознанно:
> - **Протокол строчный, а не JSON.** Ответ стримится, а невалидный JSON нельзя
>   разобрать до последнего байта; законченную строку `@point …` можно рисовать
>   сразу, пока текст ещё печатается.
> - **Отбраковка вместо фолбэка.** `isDrawable()` выбрасывает фигуры с мусорными
>   или вырожденными координатами: пустой экран честнее стрелки мимо.
> - **Рисунок требует картинки.** Без скриншота инструмент не выдаётся — модель
>   не видела цель, и координаты были бы выдуманы.
> - **Слой не попадает в скриншоты** (`setContentProtection(true)`), иначе
>   собственные обводки возвращались бы модели со следующим снимком.
> - **Парсер работает всегда.** Даже когда инструмент не выдан, строки `@point`
>   вырезаются из ответа: модель может «вспомнить» формат из истории, а сырой
>   `@point circle …` в карточке или во вставленном тексте хуже, чем без рисунка.

### 4.3 Не красть фокус

Сейчас `show()` делает `win.focus()` + `app.focus({ steal: true })` — то есть
присутствие ассистента **выкидывает тебя из приложения**. У Clicky наоборот:
открылся голосом — экран и фокус остались твоими.

Вариант, который не ломает текущий ввод:
- **Компаньон у курсора** — маленький пузырь (аватар + волна голоса + строка
  ответа), `focusable: false`, `type: 'panel'`, не активирует приложение. Живёт
  там всегда, когда ассистент «слушает/думает/говорит».
- **Карточка** — открывается поверх, только если пользователь начал печатать или
  кликнул «развернуть»; тогда фокус забирается осознанно.
- `type: 'panel'` + `focusable:false` + `app.focus` убрать; проверить на Electron
  33.2, что панель действительно не активирует приложение и не пропадает при
  Space/Mission Control (в `.scratch/blurtest` уже был зонд про accessory-режим —
  пригодится).

Цена: **1–2 дня**, эффект на ощущение — максимальный из всех пунктов.

### 4.4 Голос в ответ + «покажи, а не напиши»

- TTS: `AVSpeechSynthesizer` через helper (бесплатно, офлайн, голоса Milena/Yuri
  для RU) или облачный TTS на ключе пользователя. Начать с локального: 0 ₽ и
  мгновенно, качество «нормально».
- Озвучивать надо **первую фразу**, а не весь текст: стрим → первый чанк в TTS
  сразу, остальное договаривается. Это и даёт «ответ через 2 секунды».
- Новый контракт ответа: вместо «текст» — мини-протокол, который парсится
  инкрементально поверх текущего `for await (chunk)` в `overlay.ts`:
  ```
  @say Кнопка экспорта — справа сверху, в меню «…»
  @point 0.82 0.11 circle "Экспорт"
  @card PDF · Жми «Экспорт» → «Экспорт в PDF»
  ```
  Парсинг построчный, терпимый к недописанным строкам — в отличие от JSON,
  который в стриме не распарсить до конца.
- Режимы переосмыслить: `insert`/`analyze` → **`talk` (голос+рисунок)**,
  **`dictation` (продиктовать в поле — это у нас уже есть, `paste/index.ts`)**,
  позже `agent`.

Цена: **2 дня** на голос+протокол, ещё 1–2 на полировку озвучки.

## 5. Что дешево и сильно меняет «ощущение Clicky»

1. **Маскот.** Персонаж у курсора: idle-анимация, моргание, «слушает» (волна),
   «думает» (точки). Чистый CSS/SVG, полдня, а приложение сразу перестаёт быть
   утилитой.
2. **Копирайт.** Сейчас: «Пиши…», «Текста нет», «Скриншот окна».
   Clicky разговаривает. Переписать все строки оверлея и онбординга на живой язык
   («Вижу Slack, #general. Слушаю…»). Полдня.
3. **Онбординг-сцена, а не чек-лист.** Сейчас `onboarding/App.tsx` — три шага
   разрешений. Нужна сцена: «привет, меня зовут X» → сразу живая демонстрация
   (обведи что-нибудь на экране пользователя) → потом разрешения. Разрешения
   просить *после* вау-момента, а не до.
4. **Ответ не в простыню.** Курсивный ответ на 3 строки + рисунок + карточки
   читается в разы лучше, чем `max-height: 300px` со скроллом.
5. **Trust-бейдж.** «Смотрю на экран только по хоткею. Скриншоты не сохраняю.» —
   у нас это правда (снимок живёт в памяти, `context/screenshot.ts` пишет только
   во временную папку), но нигде не сказано. Одна строка, снимает главный страх.

## 6. Порядок работ

**P0 — сдвиг метафоры (≈1 неделя, даёт 70 % эффекта)**
1. Не красть фокус: компаньон-панель у курсора, карточка по требованию.
2. Голосовой вход (helper listen + whisper) и озвучка первой фразы.
3. Протокол `@say/@point/@card` + SVG-слой поверх экрана (сначала без маскота).
4. Копирайт + маскот + онбординг-сцена.

**P1 — «видит как Clicky» (≈1 неделя)**
5. Скриншот дисплея курсора вместо окна (+ опция «только окно» в настройках).
6. Выделение через AX (`kAXSelectedTextAttribute`) вместо ⌘C с подменой
   клипборда: мгновенно, без мигания и без риска потерять буфер. Права уже есть.
7. Память диалога: последние N реплик + описания экрана в `Session`, отправка в
   `ChatMessage[]`.
8. Диктовка как отдельный быстрый режим (уже почти готов: голос → `pasteAnswer`).

**P2 — «делает как Clicky» (недели, отдельный проект)**
9. Clicky drive: CGEvent мышь/клавиши + AX-таргетинг + Escape-прерывание.
   Каркас уже есть (`helperSendKey`, `helperActivate`).
10. Агенты/рутины/коннекторы/Chrome-расширение — это уже не «похожесть», а
    продуктовая экспансия; без P0–P1 они не нужны.

## 7. Риски и подводные камни

- **Retina-маппинг координат** — самая частая причина «стрелка мимо». Считать по
  пикселям картинки, делить на scaleFactor дисплея.
- **TCC-разрешения** растут: микрофон + запись экрана + Accessibility. Каждое
  новое разрешение — падение конверсии онбординга; поэтому разрешения после демо.
- **`focusable: false` vs ввод текста**: неактивирующая панель не получает
  клавиатуру. Нужны два окна (компаньон без фокуса + карточка с фокусом) — не
  пытаться сделать одно окно и тем и другим.
- **CGEventTap** требует Accessibility и может отваливаться (macOS выключает tap
  при таймауте) → перезапуск и watchdog, иначе «хоткей перестал работать».
- **Локальный whisper** — вес бандла (+150–500 МБ) и cold start 1–2 с; либо
  предзагрузка модели при старте приложения.
- **Модели и координаты**: gpt-4o-mini на координатах слаб. Либо двухпроходная
  схема, либо vision-модель побольше; стоимость скриншота на каждый вопрос
  (≈1–3 к изображения) вырастет кратно — нужен счётчик/лимит.
- **Стрим + TTS**: озвучивать надо по предложениям, с очередью и отменой при
  новом запросе, иначе голоса накладываются.
- **Копирование характера ≠ копирование продукта.** У Clicky за спиной команда,
  облако, платная подписка и Windows. Один в поле тянет P0+P1, но не P2.

---

## 8. Чего не копировать

- **Нокч.** Это фича конкретного железа (и требования macOS 14.2+), у нас
  якорь — курсор, и это честнее для «умного курсора».
- **3D-модели и «карточки с фото»** — дорого в разработке и в латентности, на
  первом этапе не дают ощутимой разницы.
- **Подписочная экономика** (25 talk / 150 agent в месяц) — у нас ключ
  пользователя, лимиты не нужны.
- **130 языков и 30 голосов** — на старте нужен один хороший RU-голос, а не
  матрица.

---

## 9. Итог в одном абзаце

Smart Cursor технически уже умеет почти всё нужное «под капотом» (свой native
helper, скриншот, вставка, стрим, vision) — не хватает **трёх вещей**: голоса как
входа, рисунка поверх экрана как выхода и присутствия, которое не выкидывает
пользователя из его приложения. Это P0, около недели, и именно оно превращает
«умную вставку текста» в «buddy, который смотрит на экран». Всё остальное —
агенты, драйв, рутины — из другой категории по трудозатратам и без P0 не имеет
смысла.

## 8. Агентный режим: что сделано (ноябрь 2026)

Пункт 9 из P2 («Clicky drive») реализован цепочкой: до шести действий в одном
плане, выполнение по очереди, `@look` как точка перехода и подсветка курсора на
время прогона.

**Протокол.** Тот же строчный канал, что и `@point`, — рисование и действия
делят один парсер (`src/main/response.ts`). Причина не в экономии: ответ
стримится, JSON до последнего байта не парсится, поэтому tool-call пришёл бы
целиком после того, как пользователь уже прочитал ответ. Строки:

```
@click 0.42 0.31 left «Экспорт»   @type текст   @key cmd+s
@scroll 0 -420                    @drag x1 y1 x2 y2   @wait 600
@look                             @done
```

`@look` — единственный способ получить второй заход: модель сама просит свежий
скриншот, когда без него не решить, что дальше (открылось ли меню, появилось ли
поле). Строки после `@look` не выполняются по старому кадру: план заканчивается
на нём, турн берёт свежий скриншот и модель продолжает цепочку уже по нему. Без
`@look` турн заканчивается после плана, поэтому обычный «нажми сохранить» стоит
один запрос, а не два.

**Гейты.** Три условия сразу: переключатель в настройках (`agent.enabled`,
по умолчанию выключен), Accessibility-разрешение и свежий скриншот. Без
картинки инструмент модели даже не предлагается — нажать «вслепую» хуже, чем
не нажать.

**Возврат контроля.** CGEventTap-сторож (`helper watch`) живёт только на время
плана и печатает `escape` / `mousemove`. Свои события helper помечает
`kCGEventSourceUserData`, иначе план отменял бы себя на первом же шаге.

**Координаты.** Нормализованы 0..1 против `ScreenshotInfo.area`, как у
аннотаций, и переводятся в точки один раз в раннере. `CGEventCreateMouseEvent`
и `CGWarpMouseCursorPosition` работают в top-left системе — та же, что у
Electron, поэтому переворот по Y не нужен (и был бы зеркальным багом).

**Чего нет по-прежнему.** Фоновых задач, рутин и коннекторов — это пункт 10.

### 8.2 Точное попадание: точка модели → прямоугольник системы (ноябрь 2026)

Симптом: «наводит не точно на элементы, часть действий не выполняется». Причина
не в парсере и не в маппинге — он был верный (проверено покадрово: `-R` по
`display.bounds`, 2940×1912 при 1470×956 точек, прямоугольники Accessibility
ложатся на кнопки пиксель в пиксель). Причина в том, что у модели нет пикселя:
скриншот уходит сжатым (`screenshotMaxSide: 1600`), и на глаз по такому
изображению модель ошибается на 20–60 точек. Для кнопки 24×24 это не «почти
попал», это соседняя кнопка или пустое место между иконками.

**Решение: координата модели больше не адрес, а область.** Точка отвечает на
вопрос «какой элемент», пиксель берётся из `AXUIElement`-прямоугольника.

`helper probe [pid] [x y]` (`src/main/native/helper.m`) отдаёт три вещи:

- `chain` — элемент под точкой и его предки (`AXUIElementCopyElementAtPosition`
  + `kAXParentAttribute`). Статический текст внутри кнопки так превращается в
  кнопку: берётся самый глубокий предок с `AXPress`.
- `targets` — плоский список всего нажимаемого, что есть у приложения и на
  экране: **строка меню, фокусное окно и все остальные окна** (попап-меню,
  шторка, диалог, второй документ — второй шаг плана живёт именно в них, а не в
  фокусном окне). Роль, подпись, значение, accessibility-label, `roleDescription`,
  прямоугольник, `pressable`, `editable`. Обход ограничен глубиной 40, 4000
  узлами, 400 целями и 600 мс, потому что каждое чтение атрибута — IPC в чужой
  процесс; глубина 40 нужна вебу, где кнопка лежит в тридцатом узле DOM.
- `focused` — что реально в фокусе. Это разница между «клик попал в поле» и
  «клик попал рядом, и текст сейчас уедет в другое место».

Для Chromium-приложений (Chrome, Electron, Slack, VS Code) дерево по умолчанию
выключено: окно отчитывается одной областью прокрутки. `probe` включает его
записью `AXEnhancedUserInterface` / `AXManualAccessibility` — ровно то, что
делает VoiceOver, когда приходит читать браузер. Без этого шага клики в
браузере оставались бы на координатах модели.

**Правила выбора** (`src/main/agent/targeting.ts`, чистый модуль):

1. **Подпись.** Модель пишет `@click … «Экспорт»`, и элемент с таким текстом
   находится даже при промахе в сотню точек. Сравнение терпимо к ё/е, кавычкам,
   многоточию, префиксу («Экспорт» ↔ «Экспорт в PDF»), опечатке, порядку слов и
   словоформам («Закрыть» ↔ accessibility-label «кнопка закрытия»: общий корень
   из шести букв — совпадение, пять букв у «отмена/отменить» — намеренно нет).
   Порог 0.75 для дальнего элемента и 0.55 для элемента рядом с точкой: далёкая
   вольная формулировка — это способ увести клик через всё окно, а такая же
   формулировка в двадцати точках подтверждается второй сигнал — самой точкой.
   Из двух одинаковых подписей побеждает та, что ближе к точке модели.
2. **Попадание внутрь.** Если точка уже внутри нажимаемого элемента, клик
   остаётся на ней — только подтягивается на 3 точки внутрь от края. Центр
   широкой строки или поля хуже, чем место, куда метила модель. Точка внутри
   сильнее подписи, если подпись не нашлась вовсе: галлюцинированное имя не
   должно превращать точное попадание в клик по соседнему безымянному элементу.
   Но если подпись нашлась *на другом* элементе, побеждает подпись — модель
   попадает в соседнюю кнопку чаще, чем называет не ту.
3. **Прицеливание (snap).** Нет попадания внутрь, но в радиусе 5 % диагонали
   кадра (≈87 точек на 1470×956) стоит управляющий элемент — клик идёт в его
   **центр**. Это и есть починка главного симптома: модель метила в 30 точках
   левее иконки, клик уходил в пустоту между иконками, и «действие просто не
   выполнялось». Радиус нормирован по кадру, потому что и ошибка модели
   нормирована: на 4K-дисплее те же 2 % — это уже 60 точек.
   Ограничения: элемент должен быть размером с контрол (≤360×240 — панель
   600×300 рядом с точкой это фон, а не цель), а видимое имя, не совпадающее с
   подписью, правило выключает: «Экспорт» не должен превращаться в «Удалить»,
   промах лучше чужого действия.
4. Ничего не нашлось — точка модели, `confidence 0.15`, и карточка пишет
   «· на глаз». Это единственный случай, когда клик остаётся приблизительным
   (canvas-приложения, игры, чужой процесс), и теперь он хотя бы видим.

**Что изменилось после разбора.** Старые правила срабатывали только на точную
подпись: замер на живом дереве Chrome (`probe` + `resolveTarget`, промах
искусственный) давал 100 % попаданий при верной подписи — и 5–8 % при промахе
в 40 точек, если подпись была пересказана или её не было. То есть вся точность
держалась на одном правиле, а всё остальное молча падало в «точку модели».
Три причины и три починки:

- радиус «рядом» был 20–48 точек и требовал элемента **без** имени — промах в
  40 точек в него не попадал; теперь это snap с радиусом 5 % диагонали, и он не
  требует безымянности;
- контейнер определялся по стороне (60 % ширины **или** высоты), из-за чего
  выбрасывались широкие и низкие контролы — адресная строка браузера, поиск в
  диалоге, строка тулбара; теперь контейнер — это доля **площади** (35 %), а
  поле ввода им не считается никогда;
- `roleDescription` не участвовал в сравнении, хотя у кнопок окна («кнопка
  закрытия») и у многих иконок это единственное имя, которое даёт macOS.

**Стоимость и скорость.** Дерево читается один раз на шаг, а не на пиксель.
`probe` для первого клика стартует параллельно паузе `startDelayMs`; для
следующих — **после** 55 % паузы `stepDelayMs` (≈220 мс), а не сразу: чтение
дерева в момент, когда меню ещё открывается, отдаёт элементы, разъехавшиеся по
окну, и следующий шаг целится в место, которого уже нет. Кэш дополнительно
протухает через 1.5 с и сбрасывается после любого ввода.

**Текст.** Перед `@type` проверяется `focused`: если в фокусе нажимаемый
элемент, а не поле, шаг не выполняется и карточка говорит почему. Проверка
односторонняя — приложение, которое вообще не отчитывается о фокусе, не
блокируется: ложное «не вижу поля» сломало бы печать, которая работает.

**Промпт.** `«ПОДПИСЬ»` в `@click` обязательна и описана как вторая попытка
попадания: «пиши ровно тот текст, который виден на элементе», «подпись на языке
интерфейса, а не ответа» (Search, а не «Поиск», когда кнопка подписана Search),
«иконку назови так, как она называется, включая всплывающую подсказку», «не жми
в пустое место рядом — клик мимо закрывает меню и снимает фокус».

**Снимок.** `captureScreenshot` проверяет, что картинка действительно покрывает
записанный `area`: `-R` обрезает область, вылезающую за дисплей, а
полноэкранный фолбэк снимает тот дисплей, который macOS считает первым. При
расхождении пропорций больше 2 % `area` обнуляется — тогда рисование и действия
просто не предлагаются, вместо того чтобы целиться по прямоугольнику, которого
на картинке нет.

**Проверка.** `.scratch/target-probe` — юнит-прогон правил на синтетических
прямоугольниках (`probe.ts`, включает snap, конфликт имён, широкие поля,
`roleDescription`) и живой прогон по настоящему дереву Accessibility (`live.ts`).

### 8.1 «Прошу сделать — он рисует»: почему так было и что исправлено

Симптом сформулировал владелец: «прошу запустить видео или открыть новую
вкладку — просто рисует где это». Рисование работало, действие — нет, и экран
не объяснял разницу. Причин оказалось три, и все три чинились.

**Переключатель никогда не включали.** `agent.enabled` по умолчанию `false`, и
в пользовательском `smart-cursor.json` ключа `agent` не было вообще — значит,
модель ни разу не видела `AGENT_TOOL`, а видела только `DRAW_TOOL`. «Действуй
вместо рисования» — это не то, что можно решить промптом, если инструмента
действия в запросе нет.

**Переключатель не сохранялся без «Сохранить».** Галочка в настройках жила в
черновике и уезжала на диск только по кнопке. Человек ставил её, закрывал окно
и снова получал рисунок — то есть видел ровно ту же картину, что и при
выключенном режиме. Кнопки «Сохранить» больше нет вовсе (см. 8.3): окно пишет
всё по мере правки, а мастер-переключатель идёт отдельным каналом
`agent:set-enabled` — он решает, может ли ассистент действовать вообще, и
должен быть на диске раньше, чем придёт следующий ответ.

**Негде было узнать, что режим выключен.** Карточка у курсора молчала. Теперь
она называет причину в тот момент, когда это видно: «могу и нажать за вас —
управление мышью пока выключено» с кнопкой «Включить» (и следующей кнопкой
«Открыть Универсальный доступ», если разрешения всё ещё нет). Строка появляется
не всегда, а когда есть повод: пользователь развернул карточку, на экране есть
рисунок, или сама просьба была действием (`@shared/intent` — грубый матчер
глаголов «нажми/открой/запусти/…»; он ничего не маршрутизирует, только решает,
показать ли строку).

**Промпт.** Когда оба инструмента доступны, перед ними стоит правило выбора по
глаголу (сделать vs показать), а внутри `AGENT_TOOL` — шпаргалка по прямым
способам: `@key cmd+t` вместо клика по «+», `@key space` вместо клика по плееру,
`cmd+l` вместо клика по адресной строке. Когда действие недоступно, в промпт
уходит `ACT_UNAVAILABLE` с причиной: модель обязана сказать, что нажать не
может, а не подменить ответ рисунком. Молчаливая стрелка у кнопки, которую
просили нажать, — это не выполненная просьба, а подделка ответа.

### 8.3 Настройки без кнопки «Сохранить» (ноябрь 2026)

Кнопка «Сохранить» была не удобством, а источником ровно того бага, из которого
вырос весь раздел 8.1: значение, которое видно на экране, и значение, которое
использует приложение, — разные вещи, пока их не свели вместе вручную. Поэтому
кнопки больше нет: каждое поле применяется само.

**Как.** Правка кладёт значение в черновик, эффект ждёт 450 мс тишины и пишет
снимок черновика. 450 мс — это «имя модели не пишется по буквам, а галочка уже
ощущается нажатой». `⌘S` остался и означает «записать прямо сейчас, без
паузы»: привычка старше этого окна, а без перехвата он открывал бы системный
диалог сохранения страницы поверх настроек.

**Два сторожа, без которых автоприменение — это новый класс багов.**

1. *Снимок записи* (`writtenRef`). Сравнение «черновик ≠ сохранённое» врёт,
   когда хранилище нормализует значение: хвостовой слэш в base URL, `2048.7` →
   `2049`, пробелы по краям. Черновик тогда навсегда отличается от того, что
   только что записано, и окно переписывало бы одни и те же настройки каждые
   450 мс, пока открыто. Поэтому запоминается то, что реально ушло на диск, и
   этот снимок считается применённым.
2. *Снимок неудачи* (`failedRef`). Если запись упала, повторять её по таймеру
   бессмысленно: получится одно и то же сообщение об ошибке каждые полсекунды.
   Ошибка показывается один раз, следующий заход — на новую правку, `⌘S` или
   закрытие окна.

**Поле, которое нельзя записать как есть.** Пока в поле недописанное значение
(пустой системный промпт, число токенов вне 64–8192, адрес, который ещё не
URL), запись стоит на паузе, и подвал говорит почему. Записать это означало бы
дать хранилищу молча заменить видимое значение на другое — 0 станет 64, мусор
станет пустой строкой, — то есть показать в окне не то, что используется.

**Закрытие окна.** Единственный момент, когда автоприменение может потерять
правку, — те 450 мс между клавишей и записью, а закрывают окно как раз `⌘W`.
Поэтому окно перед закрытием сообщает main-процессу `settings:hold`, а обработчик
`close` (он же ловит `⌘W` и красную кнопку) ждёт, пока запись не осядет, с
потолком 1,2 с — зависший рендерер не должен делать окно незакрываемым.

**Побочный эффект, который пришлось починить.** `settings:save` дёргал
`voice.applySettings()` на каждой записи, а это перезапуск нативного
helper-процесса. С автоприменением это означало бы перезапуск голосового ввода
на каждую паузу в наборе системного промпта, поэтому теперь он вызывается
только когда голосовые настройки действительно изменились.

### 8.4 Цепочка действий и подсветка курсора (ноябрь 2026)

Требование владельца: «в агентской работе поддерживается цепочка действий, а не
просто одно действие» и «в момент агентской работы курсор подсвечивался».

**Цепочка.** Один ответ модели — это план, а не одно действие: `normalizePlan`
пропускает до `MAX_PLAN_STEPS = 6` строк, раннер выполняет их по очереди, с
паузой `stepDelayMs` между шагами и сбросом кэша AX-дерева после каждого
(`forgetProbe`), иначе второй клик нацеливался бы по карте первого экрана.
`@look` теперь не «флаг на потом», а точка перехода: строки после него не
выполняются против старого кадра — заход заканчивается на нём, турн берёт свежий
скриншот, и модель продолжает цепочку уже по нему
(`src/main/agent/plan.ts`, `src/main/overlay.ts`). До `maxSteps` (по умолчанию 3)
таких «взглядов» за турн. Промпт просит писать известные шаги одной цепочкой и
ставит `@look` между ними, когда следующий шаг зависит от результата.

**Подсветка.** `src/main/agent/cursor.ts` + `src/renderer/cursor/` — отдельный
прозрачный слой на весь дисплей: кольцо на указателе и подпись с шагом
(«2/4 · Клик: «Экспорт»»). Слой следует за настоящим курсором на ~60 Гц, поэтому
видно, куда именно helper перенёс указатель и что сейчас нажмёт. Как и
рисовальный слой, он не берёт фокус (`focusable: false`, `showInactive`), не
ловит клики (`setIgnoreMouseEvents`) и не попадает в скриншот
(`setContentProtection`) — иначе следующая итерация увидела бы собственное
кольцо как цель. При `arming` подпись добавляет «Esc — остановить».

**Кольцо живёт весь турн, а не один план (ноябрь 2026).** Требование владельца:
«пусть обводка будет до конца и только в конце пропадает». Турн — это несколько
планов подряд: цепочка шагов, `@look`, свежий скриншот, следующая цепочка. Каждый
план заканчивается событием `done`, и раньше кольцо на нём гасло — указатель на
секунду оставался голым, а потом кольцо появлялось снова, и это читалось как
«агент остановился и зачем-то продолжил». Теперь турн предъявляет права на слой
(`beginAgentTurn`), и внутри турна `done` не гасит кольцо, а паркует его в
состояние `waiting`: то же кольцо, без счётчика шагов, с подписью «Смотрю на
экран…» и более спокойным дыханием — агент не нажимает, а читает экран заново.
Гаснет кольцо ровно в одном месте — в `finally` турна (`endAgentTurn`), то есть
при ответе, ошибке, отмене или закрытии карточки. Ссылка на турн — токен, а не
флаг: `finally` старого турна, доехавший после старта нового, не имеет права
снять чужое кольцо. `aborted` / `error` / `idle` по-прежнему гасят слой сразу,
не дожидаясь конца турна: «Стоп» и провал должны быть видны немедленно.

**Цвет.** Белое кольцо с синей обводкой и белый текст на тёмном стекле — тот же
синий `#5b78ff`/`#7b95ff`, что у карточки. Тёплого кораллового акцента больше
нет ни у кольца, ни у рисовального слоя, ни у индикатора «слушаю»: палитра
приложения — белый и синий. Общие правила и токены — `docs/style.md`.

**Проверка.** `.scratch/chain-probe` гоняет парсер и `normalizePlan` на цепочке
из четырёх шагов, `@look` в середине, `@done` и потолке в 6 шагов; скриншоты
рендера кольца — `.scratch/cursor-shot` (тёмный и светлый фон, `arming`,
`waiting`); жизненный цикл слоя на настоящем модуле в Electron —
`.scratch/ring-probe` (`main.js` — турн из двух планов не мигает, `race.js` —
устаревший релиз не гасит чужое кольцо, «Стоп» гасит сразу).

### 8.5 Проверка результата перед «Готово» (ноябрь 2026)

Требование владельца: «пусть агент проверяет, выполнена ли цель, которая была ему
поставлена, перед тем как завершить работу».

**Проблема.** До этой правки слово «Готово» было мнением модели о *своих*
действиях. Раннер публиковал его сразу после последнего шага плана, карточка
показывала, и всё это происходило, когда экран ещё никто не видел: `@done «нажал
Экспорт»` мог стоять над скриншотом, где меню так и осталось открытым. Нажал — не
значит получилось.

**Как.** `agent.verifyResult` (по умолчанию включено) добавляет к турну с
действиями один запрос `buildVerify` (`src/main/prompt.ts`): в нём список
сделанного помечен явно как «действия, а не результат», приложен **свежий**
скриншот (форсированный `captureFor`, а не `ensureFreshScreenshot` — тот отдаёт
кадр моложе 600 мс, а он снят *во время* плана), и задан один вопрос: сверь
просьбу с экраном. Ответ разбирает `readVerdict` (`src/main/agent/verdict.ts`,
чистый модуль): `@done` — это утверждение, а не шаг, и он никогда не выполняется;
`@done` вместе со строками действий — не успех, а исправление с мнением (экран, о
котором заявлено, — тот, что *до* этих строк); проза без `@done` — «не видно».
Успех идёт в карточку как `checking` → `done «Готово»`, неудача — `checking` →
`error`: слова модели о том, что реально на экране, становятся ответом.

**Бюджет.** Не больше `MAX_CHECKS = 2` проверок за турн: проверка → (если не
вышло) одна исправляющая цепочка → вторая проверка, которая уже не имеет права
действовать (`canFix: false`, инструменты в промпт не кладутся). Дороже двух не
бывает, а слепой клик без последующего взгляда не случается никогда.

**Чего проверка не делает.** Не запускается, если турн прерван (`Escape`, взятая
мышь, ошибка шага) — карточка уже объяснила причину, и вердикт о намеренно
отобранном экране был бы шумом поверх объяснения. Не запускается, если не было ни
одного действия и модель не заявляла `@done`. Не запускается без скриншота: тогда
честно пишется «результат не проверен», а не «получилось».

**Кольцо и Escape.** `checking` — фаза турна, а не конец: кольцо остаётся на
указателе с подписью «Проверяю результат…» (`src/main/agent/cursor.ts`), а не
гаснет. Escape в этот момент отменяет запрос (`overlay.cancel`), а не закрывает
карточку: это всё ещё работа, которую можно остановить. Всё это видно и в
настройках — галочка «Проверять результат по экрану» с ценой в один лишний запрос.

**Проверка кода.** `.scratch/verify-probe` (собирается `esbuild`-ом, запускается
`node`) гоняет `buildVerify` и `readVerdict`: что промпт запрещает считать действия
результатом, что последняя проверка не может действовать, что `@done` не попадает
в список шагов, и что `@click` + `@done` в одном ответе — не успех.
