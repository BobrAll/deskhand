## 3. Что именно закреплено (по сценариям, а не по файлам)

**Разбор ответа модели.** `ResponseStream` и `parseAgentLine`/`parseAnnotationLine`: все маркеры, лимиты
4000/10000/±2000/6, процентные координаты, `«»`-метки, проглатывание мусора, инвариант «любая нарезка на
чанки → тот же результат» (с двумя задокументированными исключениями — R1 в `BUGS.md`).

**Планирование и исполнение агента.** `normalizePlan` (лимиты, отбраковка по выключенным возможностям,
точка вне кадра), `readVerdict` («@done вместе с действиями — не пропуск»), `targeting` (три правила:
label/containment/snap + пороги `SNAP_MIN`/`SNAP_MAX`/`SNAP_SHARE`/`LABEL_FLOOR`), `agent/index`
(три причины недоступности, guard'ы печати и клавиш, abort по Escape и мыши, кэш probe), `cursor`
(флип подписи, follow 16 мс, токены ходов, fade).

**Провайдеры.** `readSse` (границы событий, комментарии, UTF-8 побайтово), тексты ошибок 401/402/403/404/
413/429/5xx, `[DONE]`, `message_stop`, system отдельно у Anthropic, golden-тела запросов.

**Промпт.** 16 golden-снапшотов `buildRequest` + `buildContinue`/`buildVerify`/`buildRefine`, порядок
инструментов, лимиты 12000/8000.

**Контекст и вставка.** Матрица флагов `collectContext`, деградация `selection` на osascript, порядок
`writeText → 40 мс → Cmd+V → 300 мс → restoreClipboard`, приоритет png → bookmark → html/rtf.

**Голос и жесты.** Стейт-машина `voice/index` (press → record → release → whisper → вставка, watchdog,
supersede), argv и события `voice`/`gesture`-listener'ов, аргументы whisper-cli и фильтр `(music)`.

**Настройки и IPC.** `normalizeSettings` (все clamp'ы и `sanitize*`, потеря переименованного ключа),
`store` (битый файл → `clearInvalidConfig` → memoryFallback), `secrets` (enc:/plain:, залоченный Keychain),
снапшот 56 IPC-каналов, снапшот 74 методов preload против `api.ts`.

**Окна как чистые решения.** `hotkey` (замена/потеря регистрации), `permissions` (какой источник
побеждает), `tray` (пункты и 5 кликов), `hud` (выбор стороны, клэмп, fade), `pointer` (маппинг, кольцо,
fade). Окна при этом не создаются — проверяются только решения.

**Палитра.** Итоговые значения CSS-переменных для 6 окон в обеих темах, 21 общий токен, поиск висячих
`var(--x)`.

## 4. Что НЕ покрыто и почему

### 4.1 `context/screenshot.ts` (278 строк, 0 %)

Захват экрана: `execFile` → `screencapture`/helper, `nativeImage` для downscale и JPEG-энкодинга, окно
скриншота, ретраи. Причина: единственный способ проверить — реальный захват экрана, а он (а) требует
выданного Screen Recording, (б) возвращает разное на каждой машине, (в) в тестах запрещён правилом
«тесты не трогают реальные ресурсы». Логика, которую *можно* было бы вынести (какой размер, какое
качество, когда переснимать), уже вынесена в `ensureFreshScreenshot` внутри `overlay.ts` — а он тоже
Electron-связан.
**Чем закрыто:** MANUAL_SMOKE §3 (три приложения), §4 (поток и разметка), §9.7 (скриншот выключен).

### 4.2 `llm/index.ts` и `llm/testKey.ts` (110 строк, 0 %)

`getProvider`/`resolveModel` — три строки диспетчеризации, покрывать нечего; `testApiKey` — живой
HTTP-запрос к провайдеру с настоящим ключом. Причина: правило «fetch всегда мок», а мокать `testApiKey`
целиком = тестировать мок. Провайдеры, которые он вызывает, покрыты на 100 %.
**Чем закрыто:** MANUAL_SMOKE §9.2 (смена провайдера + «Проверить и сохранить»).

### 4.3 `overlay.ts`, `windows.ts`, `index.ts` (2 565 строк, 0 %)

Три файла — вся Electron-обвязка: создание 6 окон, `webPreferences`, `whenReady`, IPC-регистрация,
жизненный цикл приложения. Их нельзя импортировать в `env: node` без мока `electron` в объёме, при
котором тест проверяет мок, а не код. Это осознанная граница: в T28 из `overlay.ts` вынесен **шов**
`turnStream.ts` (100 % покрытия, 16 тестов на фейковом провайдере) — ровно та часть, которая была
тестируемой; остальное в `overlay.ts` — окно, фокус, hold-политика, то есть Electron.
**Чем закрыто:** MANUAL_SMOKE целиком (12 разделов). Плюс косвенно: `ipc.test.ts` проверяет, что каждый
канал из `CH` имеет хендлер и что хендлеры доходят до `deps`.

### 4.4 Renderer (React, canvas, CSS) — кроме палитры

`overlay/App.tsx` (1365), `settings/App.tsx` (934), `useVoice.ts` (291), `recorder.ts` (223),
`pointer/draw.ts` (230), `hud/hud.ts` (130), `cursor/cursor.ts` (148). Причина: в проекте нет
jsdom/React Testing Library, а добавлять их — новая зависимость, которую по правилу 3 решаю не я.
Canvas-рисование (`measureLine`, `draw`) в Node вообще не выполняется. Падение на этом слое ловится
сборкой (`tsc -p tsconfig.web.json`) и глазами.
**Чем закрыто:** MANUAL_SMOKE §4, §7, §10, §11, §12 — весь визуальный слой.

## 5. Мутационная проверка (T33)

42 мутанта по P0-модулям, гонялись на изолированной копии дерева (`/tmp/mut/work`, `node_modules` —
симлинк), по одному: мутация → `npx vitest run <файл>` → откат. Поймано **41**.

Выживший один — `AnnotationStream.push` (мёртвый класс, §4.5).

Что дала проверка: три константы `targeting` (`SNAP_MIN`, `SNAP_SHARE`, `SNAP_MAX`) и `LABEL_FLOOR` не
имели ни одного теста, чей исход зависел от их значения — тесты проходили при любом числе. Плюс
`MAX_TYPE_CHARS` и `MAX_ANSWER_CHARS` проверялись *через саму константу* (`repeat(MAX_...)`), то есть
изменение числа не ломало ничего. Всё это закрыто в коммите `7d17660`; повторный прогон — 8/8.

Stryker не ставился: `@stryker-mutator/core` 10.x доступен, но требует раннер под vitest и пер-мутантный
прогон файла целиком; для 42 ручных мутантов это дороже, а задача разрешала пропустить.

## 7. Что делать дальше с покрытием

1. **Не гнаться за процентами.** 66 % строк при 92.5 % ветвей — это потолок для проекта, где треть кода
   и есть Electron-обвязка. Поднимать цифру моками `electron` = тестировать моки.
2. **A2 (мусор)** — убрать три мёртвых сущности из §4.5; после этого `annotations.ts` и `hud.ts`
   подрастут в процентах сами, без новых тестов.
3. **A1 (крупные модули)** — если `overlay.ts` будет разрезан, из него выйдут новые тестируемые швы по
   образцу `turnStream.ts` (кандидаты: hold-политика текста, сериализация `showAnnotations`).
4. **Renderer** — если понадобится, это отдельное решение про jsdom + RTL, а не «дописать тестов».
