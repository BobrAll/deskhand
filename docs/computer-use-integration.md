# Семантический бэкенд computer-use

Состояние на **8 ноября 2026**. Ветка `feature/computer-use-integration`.

---

## 1. Что изменилось

До этой ветки агентский режим знал один способ действовать: взять точку из ответа
модели, поправить её по прямоугольнику элемента из Accessibility-дерева и послать
событие мыши. Точка — это догадка о том, *где* кнопка; дерево её уточняет, но
когда дерева нет (canvas, кастомная отрисовка, приложение без AX) остаётся догадка.

Теперь у клика с подписью есть второй путь: назвать элемент и попросить локальный
сервис `cu-service` (проект `computer-use`) нажать именно его.

| | Визуальный путь | Семантический путь |
|---|---|---|
| Вход | нормализованная точка | роль и название элемента |
| Поиск цели | AX-дерево вокруг точки | AX-дерево всего окна, по идентичности |
| Действие | событие мыши по координате | `AXUIElementPerformAction` / фокус + ввод |
| Доказательство | «отправлено» | приложение подтвердило изменение |
| Побочные эффекты | курсор двигается | курсор не двигается, окно не поднимается |
| Не нашёл | клик по догадке | отказ, затем визуальный путь |

Главное свойство: **семантика — надстройка, а не зависимость.** Нет сервиса, нет
бинаря, нет доверия Accessibility, элемент не назван, сервис отказал — шаг
выполняется ровно как раньше.

---

## 2. Как это устроено

```
шаг плана (@click … «Сохранить»)
  → semanticFor()            есть ли у шага имя и обратимый аналог?
  → cuHealth()               сервис запущен и доверен? (кэш 5 с)
  → cuAct(pid, query, press) JSON-RPC по Unix-сокету
  → readResult()             verified / performedUnverified / отказ
  → решение: выполнить, откатиться на клик, или сообщить об ошибке
```

### Файлы

| Файл | Что внутри |
|---|---|
| `src/main/agent/computerUse.ts` | клиент: JSON-RPC 2.0 по Unix-сокету, обнаружение сокета и бинаря, запуск дочернего процесса, кэш здоровья |
| `src/main/agent/semantic.ts` | чистый маппинг шага в запрос и разбор ответа; без Electron, Node и I/O |
| `src/main/agent/index.ts` | вызов семантики в цикле выполнения, до визуального пути |
| `src/main/index.ts` | запуск сервиса при старте и остановка при выходе |
| `src/shared/types.ts`, `defaults.ts` | настройка `agent.semanticActions` (по умолчанию включена) |
| `src/renderer/settings/AgentTab.tsx` | переключатель с объяснением |
| `scripts/build-cu.mjs` | копирование собранного `cu-service` в `resources/` |

### Почему сервис запускает само приложение

Доверие Accessibility привязано к *ответственному* процессу. Сервис, поднятый
через LaunchServices, стартует здоровым и бесполезным: он не прочитает ни одного
элемента. Дочерний процесс уже доверенного приложения наследует грант. Поэтому
`ensureCuService()` запускает бинарь как своего ребёнка, а `stopSpawnedCuService()`
при выходе останавливает **только** тот процесс, который запустил сам: сервис,
поднятый пользователем вручную, — его.

## 3. Правила, которые не дают пути стать догадкой

**1. Нужно имя.** У клика без подписи семантической версии нет. Запрос,
собранный из координаты, был бы координатным кликом в костюме роли.

**2. Только обратимые действия.** `press` по названной кнопке и ввод в названное
поле. Перетаскивание, прокрутка и горячие клавиши семантического аналога не имеют.
`setValue` не используется: он заменяет значение целиком, а ввод — вставляет по
каретке, что и означает «впиши».

**3. Выполненное не повторяется.** `verified` и `performedUnverified` считаются
успехом. Второе означает «вызов прошёл, приложение ничего не объявило» — повтор
кликом нажал бы кнопку второй раз, что хуже неподтверждённого успеха.

**4. Таймаут не равен провалу.** Если сервис не ответил вовремя, клик мог быть
доставлен. Шаг сообщается как неудачный, но повторно мышью не выполняется: решение
принимает проверка по свежему экрану.

**5. Отказ откатывается на визуальный путь.** «Элемент не найден под таким
именем» ничего не изменило, и точка модели остаётся лучшим оставшимся свидетельством.

## 4. Настройка

`agent.semanticActions` (по умолчанию `true`). Выключено — сервис не запускается,
все шаги идут визуальным путём. Настройка не влияет на разрешения: она
переключает маршрут, а не права.

Переменные окружения для отладки:

| Переменная | Назначение |
|---|---|
| `SMART_CURSOR_CU_SOCKET` | путь к сокету (по умолчанию `~/Library/Application Support/ComputerUse/control.sock`) |
| `SMART_CURSOR_CU_BINARY` | путь к `cu-service`, если он не рядом с приложением |
| `SMART_CURSOR_CU_PROJECT` | каталог проекта `computer-use` для `npm run build:cu` |

кнопки в приложениях разработчика, хуже падающего теста.

## 6. Что проверено вживую

На этой машине, против запущенного `cu-service`:

- `health` — сервис доверен, методы на месте;
- `snapshot` — дерево активного окна читается;
- `resolve` по `title` находит кнопку, по `text` — отказывает как на неоднозначный;
- `cuActByLabel` выполняет `press` по кнопке Chrome: `verified`, `confidence 0.90`,
  `cursorMoved: false`, `frontmostChanged: false`;
- сервис переживает `focus` — до исправления этой операции он падал с `SIGSEGV`.

### Три дефекта, найденные на первом реальном прогоне

Первая версия прошла тесты и «проверку вживую», которая на деле проверяла только
`health` и `resolve`. Настоящий прогон вскрыл три ошибки — все в моём коде, кроме
последней:

| Дефект | Симптом | Причина |
|---|---|---|
| Отказ не откатывался | шаг падал с ошибкой, клик не происходил | `refused` возвращался как `performed: true`, и визуальный путь не запускался |
| `text` как основное поле | «Назад» → 8 кандидатов → отказ | `text` — подстрочный матч по склейке title+aria+value; `title` даёт 0.90 против 0.53 |
| Краш сервиса на `focus`/`select` | `SIGSEGV` в `Action.description` | `axAction ?? "\(self)"` — рекурсия, когда у действия нет AX-имени |

Первый дефект — самый показательный: тесты проверяли `readResult` (он отвечал
правильно) и `semanticFor`, но не то, как раннер использует вердикт. Решение,
принятое между двумя проверенными функциями, не проверял никто.

Второй: `text` был выбран как «единственное поле, которое понимает подпись».
Фактически он самый слабый, и на обычных словах уходит в неоднозначность.
Теперь запросы идут каскадом от сильных к слабому, а `role` сужает слабый.

Третий — не в smart-cursor: сервис падал на действиях без AX-имени. Исправлено
в `computer-use` (`Actions.swift`), с регрессионным тестом.

### Что этим не доказано

`act` проверялся на кнопках навигации Chrome. Систематического прогона по
Finder, VS Code и Blender — критериев приёмки самого `computer-use` — не было.
До него цифру «работает» считать подтверждённой нельзя.

## 7. Что осталось

| Разрыв | Последствие |
|---|---|
| `cu-service` собирается только из соседнего проекта | В CI нужен либо сабмодуль, либо артефакт; сейчас `build:cu` тихо пропускает шаг |
| Бинарь в `resources/` — debug-сборка из `.build/debug` | Для поставки нужен release и, в идеале, universal |
| Нет `snapshot`-пути в клиенте | Модель не видит AX-дерево как структуру, только картинку; это следующий шаг к сокращению раундов |
| Имя элемента иногда лежит в `AXDescription` и недостижимо для резолвера | В таких приложениях шаг всегда откатывается на клик: это работает, но семантики там нет |
| Каскад делает до 5 вызовов на шаг в худшем случае | При промахе это лишние ~100 мс; при попадании — один вызов |
| Двойной клик, drag, scroll остаются визуальными | Семантического аналога у них нет, и притворяться, что есть, не нужно |
| Проверка по свежему экрану не знает о `notifications` сервиса | Уведомления уже приходят в `CuActionResult`, но в вердикт не попадают |
