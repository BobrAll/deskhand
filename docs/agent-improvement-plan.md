План улучшения агентского режима Deskhand

Подготовлен 6 ноября 2026 года. Основание: текущая рабочая копия проекта, существующая локальная трассировка, документация OpenAI и Apple, контракт доступного в этой сессии инструмента Codex Computer Use. В рабочей копии есть незакоммиченные изменения; этот документ описывает её состояние, а не только HEAD.

**Главная рекомендация: развивать агент как систему адресных инструментов с проверяемым состоянием.** Основной выигрыш во времени искать в сокращении обращений к модели; точность повышать привязкой действий к наблюдённым элементам и конкретному окну. Нативная основа macOS уже есть, поэтому полная перепись приложения не нужна.

**Какие принципы Codex можно перенести.**

Документация подтверждает использование разрешений Screen Recording и Accessibility на macOS и отдельных интеграций для браузера и приложений. Она не раскрывает полную нативную реализацию Codex. [Computer Use](https://learn.chatgpt.com/docs/computer-use).

В контракте инструмента `cua_repl`, доступного в этой сессии, непосредственно видны:

- Сохраняемые объекты приложения и вкладки, отдельные адресаты команд.
- Чтение Accessibility-дерева; по умолчанию возможна передача только его изменений.
- `click(elementIndex)`, `setValue`, `selectText`, поддерживаемые дополнительные действия элемента; координаты доступны как запасной способ.
- Обновление дерева после действий и запрет повторного использования устаревших индексов.
- Объединение короткой детерминированной серии действий и нового наблюдения в один вызов.
- Ожидание внутри операций получения состояния, без обязательного внешнего `sleep`.
- Отдельный путь через DOM/локаторы для поддерживаемых браузерных вкладок.

Это наблюдаемый контракт инструмента, не результат исследования его закрытого исходного кода. Постоянный процесс helper, AXObserver и ScreenCaptureKit ниже — предлагаемые решения для Deskhand. Утверждать, что Codex реализован именно так, оснований нет.

Публичный API OpenAI допускает собственные UI-инструменты и среду исполнения с сохранением сессии. Поэтому можно сохранить Electron и существующие провайдеры, добавив более строгий контракт инструментов. Полный JavaScript REPL не требуется для первого улучшения: достаточно типизированных команд и коротких последовательностей с ограничениями. [Computer use](https://developers.openai.com/api/docs/guides/tools-computer-use), [integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration).

**Что уже работает и должно стать основой.**

В проекте есть observe → act → observe, повторное получение экрана, AX-поиск элементов, проверка смены PID, ограниченное восстановление, история попыток и защита повторов. Ни один из этих выводов сам по себе не доказывает причину конкретного неудачного пользовательского запроса. Для этого нужны воспроизводимые сценарии и отдельная оценка результата.

**Предлагаемый контракт исполнения.**

```text
Запрос пользователя
  → выбор возможности по требуемому результату
  → адресат: приложение / окно / вкладка
  → согласованное наблюдение
  → короткая полностью валидированная серия действий
  → локальная проверка состояния
  → результат либо следующий модельный раунд
```

Наблюдение содержит `observationId`, PID, window/display/tab ID при наличии, геометрию и преобразование координат, время, ревизию, доступные действия и ссылки на элементы. Ссылки действуют в пределах известной ревизии; это не вечные глобальные ID. Действие содержит адресата, ссылку на наблюдение, предусловия, ожидаемый результат и deadline.

Снимок и AX нельзя считать атомарными только потому, что они упакованы в один объект. Проверять идентичность и ревизию до и после получения данных; изменившееся состояние пересобирать. При смене активного приложения обязательно заново наблюдать экран и проверять получателя ввода. В том же приложении смена окна, вкладки, модального диалога и геометрии также инвалидирует затронутые ссылки.

Результат исполнения различает `not_sent`, `dispatched`, `partial`, `unknown`, `verified`. Таймаут не равен отсутствию эффекта. После `partial/unknown` сначала проверять состояние, особенно для действий, которые нельзя безопасно повторить. Для глобального CGEvent остаётся гонка с внешним вводом: проверки уменьшают её, но не делают управление другим приложением атомарным.

**Порядок реализации и критерии готовности.**

| Этап | Работы | Проверяемый результат |
| --- | --- | --- |
| 0. Воспроизводимая исходная точка | Расширить текущие метрики; зафиксировать версии, настройки и сценарии | Есть baseline качества и времени, отдельный конечный outcome, один способ повторить сравнение |
| 1. Целостность действий и адресата | Правильное focused window; binding observation/window; обработка EOF/length; запрет молчаливого усечения; отмена native operation | Оборванный план не запускается; смена окна останавливает устаревшее действие; Stop прекращает ввод |
| 2. Семантическое управление macOS | Постоянный helper; адресные AX-команды; ссылки на элементы; уведомления и проверка результата | Поддерживаемые кнопки/поля управляются без расчёта клика; неподдерживаемые возможности дают явный fallback |
| 3. Меньше обращений к модели | Ранний выбор инструмента; короткие серии; локальные postconditions; единая оценка прогресса и завершения | Простая UI-команда не требует ещё одного LLM-вердикта при уже подтверждённом результате; поиск не требует desktop preflight |
| 4. Наблюдение и ожидания | AX diff; ожидание условий; адресный capture в памяти; точная геометрия | Быстрый UI не ждёт фиксированные сотни миллисекунд; медленный не получает преждевременный ввод |
| 5. Браузерный адаптер и сравнение моделей | Подключённые вкладки, DOM/AX локаторы, адаптеры провайдеров, A/B на той же приёмке | Меньше ошибочных кликов и модельных раундов на веб-сценариях; выбор модели подтверждён измерениями |

Этапы 0–1 — первый инкремент. Этапы 2–3 — основной архитектурный выигрыш. Подготовку маршрутизации из этапа 3 можно вести параллельно с helper, но включать новый путь только после проверок этапа 1. Этапы 4–5 выпускать по отдельности, чтобы было видно, какое изменение помогло.

Для этапа 0 расширить существующий журнал, а не заводить второй: типизированные события и разрешённые поля, build/config ID, backend и enum причины выбора, TTFT, число токенов, размеры наблюдения, время ожиданий, итоговый outcome/reason. Содержимое запросов, ввода, AX-дерева, URL с данными и изображения не логировать. Состояние и изображения для текущего исполнения держать в памяти; fixture ID использовать только для заранее заданных тестов. Общий deadline должен покрывать LLM, helper, восстановление и проверку, отдельно учитывая пользовательские паузы.

Для этапа 1 сохранить текущий текстовый протокол на переходный период, но сначала добавить достоверный статус завершения ответа и строгую валидацию всей серии. Затем перейти к общей схеме tool calls для провайдеров. Структурированный формат сам по себе не гарантирует правильную цель. Не ускорять исполнение запуском частично пришедших команд. Это соответствует рекомендации API о запрете частично сгенерированного действия. [Integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration).

Отмена должна доходить до нативного исполнителя: command ID, cancellation, прекращение очереди, безопасное отпускание зажатых клавиш/кнопок. Сообщение «Остановлено» публиковать после подтверждения остановки; до этого — «Останавливаю». Для отказа helper сохранять известность частичного эффекта. Проверить кириллицу, emoji, IME и длинный текст; лимит показывать явно либо применять проверяемый транспорт без усечения.

Для этапа 2 запустить helper как дочерний процесс на сессию с JSON-RPC по pipe: request IDs, timeout, cancellation, health/restart, один последовательный исполнитель изменений. Предоставить `observe`, `press`, `setValue`, `selectText`, `waitFor`, а существующие `click/key/type` оставить для интерфейсов без нужной семантики. Действовать только через реально поддерживаемые элементом AX actions; после изменения значения проверять, что приложение приняло его. Apple предоставляет [AXUIElementPerformAction](https://developer.apple.com/documentation/applicationservices/1462091-axuielementperformaction) и [AXUIElementSetAttributeValue](https://developer.apple.com/documentation/applicationservices/1460434-axuielementsetattributevalue), но приложения могут не поддерживать операцию.

Выбор цели строить по наблюдённой ссылке и контексту: role, окно, контейнер, label, доступность. При двух одинаковых кнопках уточнять цель по дереву/области; не считать нынешние эвристические confidence вероятностями. Для canvas и слабого AX оставлять визуальный путь с актуальным кадром, увеличением нужной области и проверкой эффекта.

Для этапа 3 выбирать возможность по результату: общедоступные сведения → web search; явно заданный переход → browser navigation; взаимодействие с наблюдаемым интерфейсом → UI backend; доступная структурированная интеграция → её API. Не добавлять таблицы названий сайтов и приложений в логику намерений. Неоднозначный запрос может потребовать компактного решения модели, но не обязательного полного visual preflight.

Короткие серии объединять только внутри проверенного состояния: например, фокус известного поля, заполнение, проверка значения. После перехода, появления диалога или смены адресата — новое наблюдение. Готовность проверять локально, когда критерий объективен; модель возвращать в цикл для выбора следующего шага или смысловой оценки. При отсутствии доказательства результата не пропускать проверку ради скорости. Существующий пропуск повторной финальной проверки сохранить и расширить до проверяемых postconditions.

Для этапа 4 уведомления AX/NSWorkspace инвалидируют кэш и запускают проверку условия. Нужны короткий ограниченный polling и timeout там, где уведомления отсутствуют. Событие не является доказательством готовности; анимированный экран также не обязан стать полностью неподвижным. Проверять нужный элемент/область. Apple описывает уведомления и их возможную неподдерживаемость в [AXObserverAddNotification](https://developer.apple.com/documentation/applicationservices/1462089-axobserveraddnotification).

Прототип захвата — ScreenCaptureKit с конкретным window/display ID и кадром в памяти; проверить поддержку на минимальной целевой macOS и работу исключения оверлеев. [SCScreenshotManager](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager). Сохранять координатное преобразование для Retina, crop и нескольких мониторов: одинаковые пропорции изображения недостаточны. Общий принцип согласования снимка и координат описан в [driver reference](https://developers.openai.com/api/docs/guides/tools-computer-use-sdk-drivers).

Передавать модели изменения AX с явной базовой ревизией; если она потеряна, отправлять полный снимок дерева. Кэшировать структуру и доступные возможности, но не использовать старое состояние как подтверждение результата. На смене приложения сохранять обязательный свежий экран. Защиту повторов дополнить состоянием цели и результатом действия: анимация или часы не должны превращать повтор того же неэффективного клика в новую стратегию.

Для этапа 5 браузер должен сохранять правильные профиль и вкладку пользователя. Отдельный новый браузерный профиль не заменяет текущую авторизованную сессию. Начать с одного поддерживаемого способа подключения и capabilities, затем расширять; маршрутизация не должна зависеть от списка сайтов. Автовыбор более сильной модели добавлять только после сравнения качества, задержки и стоимости: сначала измерить доступные конфигурации на одинаковых задачах. Ограниченный кодовый runtime можно исследовать позже; выполнять произвольный код модели в Electron main process не требуется.

**Приёмка, без которой ускорение нельзя считать улучшением.**

Зафиксировать 24 сценария и выполнить по пять повторов на baseline и кандидате: 120 запусков каждой версии. Порядок версий чередовать; использовать одинаковые модель, endpoint, настройки, начальные состояния и оборудование. Cold/warm start учитывать отдельно. Конкурентные прогоны в одном приложении не запускать. Названия конкретных приложений и сайтов допустимы в regression fixtures; в runtime routing и инструкции инструментов их не переносить.

Набор должен включать публичный поиск, открытие заданного адреса, форму, открытие документа, переключение настройки, переход между приложениями, два окна одного PID, смену вкладки, modal, одинаковые подписи, задержку загрузки, отсутствие AX, canvas, два монитора одинаковых пропорций, Retina, Unicode/IME, пользовательскую смену фокуса, Stop во время ввода, timeout и обрыв модельного потока. Нативные действия проверять в специальном тестовом приложении с полями и окнами, а не на пользовательских документах.

Успех задавать заранее и оценивать независимо от ответа модели: состояние тестового приложения, факт открытия нужного документа или ручная проверка результата без сохранения снимков. Отдельно считать успех задачи, ложное «готово», неверного адресата, отмену, время первого действия и завершения, модельные раунды, повторы, стоимость. Неуспешные быстрые остановки не должны искусственно улучшать метрику скорости: показывать время всех попыток и успешных попыток раздельно, вместе с success rate.

Предварительные цели выпуска: не менее 90% успешных задач на согласованной выборке, ноль ложных подтверждений и ввода в неверную цель в обязательных тестах; снижение медианы времени минимум на 30%, p95 минимум на 20%, модельных раундов на 25% без ухудшения качества. Это цели для проверки, а не прогноз по текущим 25 запросам. Малый размер выборки не доказывает отсутствие ошибок вне неё; фиксировать число прогонов и неопределённость оценки.

Каждый новый backend включать отдельно флагом, с возможностью возврата. Fallback после неизвестного эффекта сначала наблюдает состояние и не повторяет изменение вслепую. Сохранять текущие разрешения, подтверждения значимых действий и передачу управления пользователю.

Первый практический пакет: измеримый baseline, исправление выбора окна, запрет исполнения усечённого плана/текста и реальная отмена helper. После него — адресные AX-действия и устранение лишних модельных проверок. Полное фоновое управление, как в Codex, оставить отдельным исследованием: из наличия Accessibility API не следует возможность надёжно управлять любым приложением без фокуса.
